# Prospective list.sort key compatibility candidate, October 30

The complete joint public-feedback screen at source 96fbe8a40b22dbf44ffc652335c0e971cfa48a4a produced no full solves in either arm. Two final execution failures contained list.sort(key=...), one with a lambda and one with a named key. A third execution failure had no unsupported AST kind and is not attributed to this syntax limitation.

This separate candidate implements standard stable list.sort key/reverse semantics for bounded local lists. Keys may be None, an existing named one-argument function, len, abs or a one-argument lambda evaluated inside the bounded interpreter. Keyword arguments and lambdas remain rejected outside this specific context. No candidate text is sent to host eval/exec, no first-class callable crosses the value boundary, and source, AST-node, item, string, function/depth and step limits remain unchanged. Input mutation is still rejected.

The public language contract is updated to describe exactly that addition. Task algorithms, fixtures, reference solutions, hidden tests and reward weights are unchanged. This changes the accepted language and declared contract; it is a compatibility experiment, not a claim that the original responses followed their original no-keyword/no-lambda instructions. It does not combine helper-preservation instructions, extra review turns or source-diagnostic feedback.

Eight local tests passed against trusted static CPython fixtures: lambda closure, stable ties and reverse order; named and existing builtin keys; one key evaluation per item in input order; None keys and in-place return value; rejection outside the narrow context; callback step limits; input mutation protection; and propagated callback errors. Only trusted static test code is executed by CPython; model responses must remain inside the bounded interpreter.

Exact-source ruOS native qualification, regression checks and saved-response counterfactual replay are still pending. Any replay recovery is posthoc compatibility evidence, not fresh model improvement. A fresh disjoint matched model comparison and disjoint confirmation remain required before improvement claims, with Arena held-out evaluation required for leaderboard claims. No paid caller, new spending cap, purchase, training job, Arena request, HF replacement or runtime-image replacement is introduced here. Frozen v12 and rollback v11 remain unchanged.
