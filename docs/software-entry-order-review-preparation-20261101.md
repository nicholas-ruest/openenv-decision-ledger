# Public entry-order relation feedback: prospective preparation

The known baseline partial from the closed syntax-note screen reverses a discovery list before computing parent-dependent statuses. Reversing discovery order does not guarantee that parents precede descendants. In a private posthoc control, replacing only that ordering statement with dependency order changed Native reward from 0.95 to 1.0, while other functions remained identical. The original response and closed screen were preserved. This is a diagnostic edit by the investigator, not a new model solve, selected comparison or improvement claim.

An earlier parent-status reminder comparison failed selection. This preparation does not retry that cue, the closed initial self-check, helper guidance or syntax-note studies. Instead, both prospective arms receive the same public relation reminder and identical initial instructions. Both execute the same bounded relation check locally; only treatment sees the computed counterexample during review. The relation says that permuting the entries list must preserve the returned path-to-boolean mapping, as entry order is not part of the published task contract.

The diagnostic reads only the examples in the original visible observation. It uses the unchanged bounded Native interpreter to compare outputs across permutations. It never uses the supplied expected answers, a reference implementation or hidden grading data. Feedback exposes a public-example index and entry-position permutation, not a repaired program or expected output. A consistent result can still be wrong. Program rejection/runtime failures remain unavailable diagnostics, and unexpected Native infrastructure errors propagate.

Both arms use two content-only responses with the same action schema, original module and final unchanged Native grading. The relation reminder is common; computed counterexample exposure is the only treatment difference. All review and terminal observations must consume the existing completion/context allowance.
